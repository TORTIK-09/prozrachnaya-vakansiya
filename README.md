# Прозрачная вакансия

Сервис получает вакансии Калининградской области с портала «Работа в России» и формирует отчёт о том, насколько понятно описаны условия работы. По каждой вакансии он находит пропуски, неоднозначности и противоречия и подсказывает редактору, что уточнить у работодателя.

Тестовое задание онлайн-отбора КАНТКОД.

## Быстрая проверка

Нужны Python 3.12 и [uv](https://docs.astral.sh/uv/).

```
uv sync
uv run python -m pv check examples/sample_vacancies.json --out reports/check.json
```

Отчёт появится в `reports/check.json`. Свой набор проверяется так же — подставьте путь к своему JSON в формате ответа API. К порталу проверочный режим не обращается.

Посмотреть отчёт глазами:

```
uv run python -m pv web
```

Панель откроется на http://127.0.0.1:8085: список вакансий, замечания, цитаты, подсвеченные прямо в полях вакансии, загрузка своего JSON кнопкой.

## Модель и запуск без покупки аккаунта

Сервис работает с любой моделью по OpenAI-совместимому протоколу. По умолчанию он ищет локальную [Ollama](https://ollama.com) — она бесплатна, не требует ни ключа, ни регистрации:

```
ollama pull qwen2.5:3b
uv run python -m pv check examples/sample_vacancies.json --out reports/check.json
```

Если Ollama запущена, сервис находит её сам. Другая модель или провайдер задаются тремя настройками:

| Настройка | Переменная | Пример |
|---|---|---|
| Адрес | `PV_LLM_BASE_URL` | `http://127.0.0.1:11434/v1` — Ollama; `https://openrouter.ai/api/v1` — облачный провайдер с бесплатными моделями |
| Модель | `PV_LLM_MODEL` | `qwen2.5:3b` |
| Ключ | `PV_LLM_API_KEY` | для локальной модели не нужен |

Ключ хранится только в переменной окружения или в файле `.env`, который в репозиторий не попадает (образец — `.env.example`).

### Автоподключение и настройка модели

Сервис сам находит запущенную модель: сначала ту, что задана настройками, иначе локальную Ollama. Модель опознаётся по провайдеру и имени. Если сервис встречает её впервые, он **настраивает её под задачу**: прогоняет по 22 размеченным вакансиям, сверяет ответы с разметкой и отключает виды замечаний, в которых эта модель ошибается чаще, чем попадает. Результат сохраняется в `reports/profiles/`, и в следующий раз модель узнаётся без повторной настройки.

- В панели настройка запускается сама. Пока она идёт, вверху висит уведомление с оценкой оставшегося времени; по окончании его сменяет сообщение об итоге, которое остаётся, пока его не закроют кнопкой.
- Из командной строки: `uv run python -m pv calibrate`. Команды `check` и `run` незнакомую модель используют сразу, без настройки, и предупреждают об этом.

Это настройка, а не дообучение: веса модели не меняются — меняется то, какую часть её ответа сервис пускает в отчёт.

Если модель недоступна, сервис не падает: он сообщает об этом, выполняет проверки правилами и ставит в отчёте `"model": {"used": false}`. Флаг `--no-llm` отключает модель явно.

## Где применяется ИИ

Обработка одной вакансии — два шага (`pv/analyze/`):

1. **Правила** (`rules.py`) находят то, что видно из структурированных полей: пропуски, расхождение чисел и текста (опыт 0 в поле и «не менее 5 лет» в описании), размытый график, неполный адрес, противоречие «дистанционно» и «в офисе».
2. **Модель** (`ai.py`) получает поля вакансии и разбирает её сама, без подсказок от правил: ищет размытые формулировки и смысловые противоречия между полями, для каждого замечания пишет суть и рекомендацию.
3. **Объединение** (`__init__.py`): у каждого замечания видно, кто видит проблему, — правило, модель или оба. Если видят оба, замечание одно: формулировка берётся у модели, цитаты — у правила. От модели берётся и то, чего правила не нашли.

### Что алгоритм узнаёт из самих вакансий

Опыт «0» в поле встречается почти в половине вакансий портала и значит две разные вещи: опыт действительно не нужен — или поле забыли заполнить. Правила различают их так:

- **Опыт не нужен**, если так сказано в любом поле («без опыта», «обучение на месте», «требования к стажу не предъявляются») или должность начальная (помощник, стажёр, ученик). Замечания нет.
- **Вопрос работодателю**, если должность старшая или руководящая (начальник, ведущий, главный, заведующий), а про опыт в тексте ни слова.
- **Вопрос работодателю**, если в этой профессии на портале опыт требуют почти всегда. Эти нормы алгоритм считает сам по вакансиям портала: у заведующих опыт требуется в 19 вакансиях из 19, у поваров — в 32 из 37, у уборщиков — в 2 из 26. Поэтому «повар, опыт 0» вызывает вопрос, а «уборщик, опыт 0» — нет.
- В остальных случаях ноль принимается как есть.

Таблица норм лежит в `pv/data/experience_norms.json` (посчитана по 400 вакансиям) и пересчитывается командой `uv run python -m pv learn`. На 400 живых вакансиях из 189 с опытом «0» правила приняли как есть 177, задали вопрос по 11 и нашли одно прямое противоречие с текстом.

Ответу модели сервис на слово не верит. Каждая цитата должна дословно находиться в названном поле вакансии — иначе замечание отбрасывается. Пропуски от модели в отчёт не идут: она склонна считать пропуском то, что указано в другом поле. Виды замечаний, в которых модель оказалась ненадёжной при настройке, отбрасываются. Текст вакансии передаётся модели как данные, отдельно от инструкции.

В отчёте у каждого замечания есть поле `source`: `rule` — нашло правило, `llm` — нашла модель.

## Статистика: правила, модель и вместе

Страница панели «Статистика» (http://127.0.0.1:8085/stats) сравнивает три способа работы на размеченных вакансиях: только правила, только модель, вместе — до и после настройки модели. Для каждого показано, сколько обязательных замечаний найдено, сколько лишних, сколько времени уходит на вакансию, и что из этого следует. Без подключённой модели страница показывает одни правила.

Размеченных наборов два: десять учебных вакансий организаторов (`eval/gold.json`) и двенадцать собственных, где проблема выражена смыслом, а не привычными словами (`eval/extra_vacancies.json`, `eval/extra_gold.json`). Разметка обоих наборов наша; эталон жюри нам неизвестен.

## Рабочий режим

```
uv run python -m pv run                 # загрузить вакансии из API и собрать отчёт
uv run python -m pv run --max 500       # с другим лимитом
uv run python -m pv schedule            # работать постоянно и запускать то же самое по расписанию
```

- Вакансии загружаются постранично (по 100), пока не набран лимит: при лимите 200 это две страницы.
- Отчёт пишется в `reports/latest.json`, прежний уходит в `reports/history/`, если содержимое изменилось.
- **Повторный запуск** на тех же данных даёт тот же отчёт: одна запись на ID вакансии, неизменившиеся вакансии берутся из кэша и в модель заново не отправляются.
- **Портал недоступен** — сервис сообщает об ошибке, завершает работу с ненулевым кодом, записывает `reports/last_error.json` и не трогает последний успешный отчёт.

Расписание — три равноценных способа, все запускают одну и ту же команду `python -m pv run`:

| Способ | Файл |
|---|---|
| Встроенный планировщик | `python -m pv schedule`, cron-выражение в настройке `schedule` |
| GitHub Actions | `.github/workflows/schedule.yml` — по расписанию и кнопкой «Run workflow» |
| Планировщик ОС | `automation/windows_task.ps1`, `automation/crontab.example` |

**Обработка начинается** в `pv/cli.py` (`python -m pv …`); файл расписания — `.github/workflows/schedule.yml`.

## Формат отчёта

Пример на учебных данных — `examples/sample_report.json`.

```json
{
  "generated_at": "2026-11-24T18:30:00+02:00",
  "mode": "file",
  "source": "sample_vacancies.json",
  "model": {"provider": "ollama", "model": "qwen2.5:3b", "used": true},
  "stats": {"vacancies": 10, "with_findings": 6, "findings": 18},
  "vacancies": [
    {
      "id": "DEMO-39-004",
      "url": null,
      "title": "Оператор контактного центра",
      "company": "Учебная организация «Балтика»",
      "findings": [
        {
          "topic": "location",
          "kind": "contradiction",
          "field": "duty",
          "quote": "полностью дистанционная из любого города",
          "problem": "В описании одновременно заявлены дистанционная работа и обязательное присутствие в офисе.",
          "recommendation": "Уточните у работодателя формат работы: дистанционный, в офисе или смешанный, и в какие дни нужно присутствие.",
          "conflict_with": {"field": "requirement.qualification", "quote": "Обязательное ежедневное присутствие в офисе"},
          "source": "rule"
        }
      ],
      "fields": {"job-name": "Оператор контактного центра", "duty": "…"}
    }
  ]
}
```

**Запись вакансии**

| Поле | Что в нём |
|---|---|
| `id` | ID вакансии из источника |
| `url` | ссылка на карточку (`vac_url`); `null`, если её нет в данных |
| `title`, `company` | название должности и организация |
| `findings` | массив замечаний; пустой, если замечаний нет |
| `fields` | значения полей источника — чтобы видеть цитаты в контексте |
| `error` | появляется, только если анализ этой вакансии завершился сбоем |

**Замечание**

| Поле | Что в нём |
|---|---|
| `topic` | тема: `title` — название должности, `duties` — обязанности, `requirements` — требования, `salary` — оплата, `schedule` — график, `location` — место работы, `employment` — тип занятости |
| `kind` | `missing` — пропуск, `ambiguous` — неоднозначность, `contradiction` — противоречие |
| `field` | поле источника, путь как в ответе API (`duty`, `requirement.qualification`, `addresses.address[].location` …) |
| `quote` | дословная цитата или значение из этого поля; у пропуска — пустая строка |
| `problem` | суть проблемы |
| `recommendation` | что именно уточнить у работодателя |
| `conflict_with` | только у противоречия: второе исходное значение — `{"field", "quote"}` |
| `source` | кто видит проблему: `rule` — только правило, `llm` — только модель, `both` — оба (тогда формулировка от модели, цитаты от правила) |

В `stats` кроме основных чисел есть служебные: сколько записей пропущено без ID, сколько взято из кэша, сколько замечаний отброшено проверкой цитат.

## Свой сценарий: черновик резюме под вакансию

- **Кому помогает:** соискателю и карьерному консультанту центра занятости.
- **Какие данные использует:** запись вакансии из готового отчёта — поля `job-name`, `duty`, `requirements`, `requirement.*` и найденные замечания; работает и на учебном наборе, и на вакансиях, загруженных из API региона 39.
- **Что выдаёт:** черновик резюме, где навыки и пункты опыта переставлены по близости к вакансии; список того, чего вакансия требует, а резюме не подтверждает; вопросы работодателю по замечаниям отчёта; черновик сопроводительного письма.

Опыт, навыки и образование берутся только из исходного резюме: сценарий отбирает и переставляет, но ничего не дописывает. Это проверяется тестом. Резюме в `examples/sample_resumes.json` вымышленные.

```
uv run python -m pv resume --resume RES-03 --vacancy DEMO-39-003 --report reports/check.json
```

В панели — вкладка «Резюме под вакансию».

## Проверки

```
uv run pytest
```

96 тестов: загрузка и разбор страниц, нормализация, правила на учебном наборе и на приёмах, которых в нём нет, шаг с моделью и её настройка на подставном клиенте, отчёт, кэш, поведение при сбое портала, панель, сценарий с резюме. Тесты не обращаются к сети.

Сравнение отчёта с разметкой:

```
uv run python eval/score.py reports/check.json
```

На учебном наборе правила без модели находят все 13 обязательных замечаний и не дают лишних; четыре понятные вакансии остаются без замечаний. На собственных примерах со смысловыми проблемами правила не находят ничего — это работа модели.

## Устройство

```
источник (API или файл) → нормализация → анализатор → отчёт
   pv/source.py            pv/normalize.py   pv/analyze/   pv/report.py
```

| Файл | Что в нём |
|---|---|
| `pv/cli.py` | команды `run`, `check`, `schedule`, `web`, `calibrate`, `learn`, `resume` |
| `pv/models.py` | общие типы: вакансия, замечание, проверка замечания |
| `pv/llm.py` | клиент модели |
| `pv/calibrate.py`, `pv/analyze/profile.py` | настройка модели и её профиль |
| `eval/` | размеченные наборы и скрипт сравнения |
| `pv/web.py`, `pv/static/` | панель |
| `pv/extra/resume.py` | сценарий с резюме |
| `docs/spec/` | общий контракт и спецификации частей |

Контактные данные из вакансий (телефоны, почта, контактное лицо) отбрасываются при нормализации: в модель и в отчёт они не попадают.
