## Стек

Python 3.12, зависимости через `uv` (`uv sync`, запуск — `uv run ...`). Тесты — `pytest`. Новую зависимость добавляет тот, кому она нужна (`uv add ...`), и пишет об этом в общий чат: файл `uv.lock` общий, правки в нём конфликтуют.

## Как данные идут через программу

```
источник (API или файл) → нормализация → анализатор → отчёт
   pv/source.py            pv/normalize.py   pv/analyze     pv/report.py
```

1. `source` отдаёт список сырых объектов вакансий — одинаково из API и из файла.
2. `normalize` превращает каждый в `Vacancy` (`pv/models.py`).
3. `analyze(v, llm)` возвращает список `Finding` для одной вакансии.
4. `report` собирает отчёт, проверяет замечания функцией `validate` и записывает файл.

Граница между частями 1 и 2 — одна функция:

```python
# pv/analyze/__init__.py
def analyze(v: Vacancy, llm: LLM | None = None) -> list[Finding]: ...
```

Требования к ней:
- чистая: один и тот же вход даёт тот же результат, без записи файлов и глобального состояния;
- её можно вызывать из нескольких потоков одновременно;
- `llm is None` — работают только правила, функция не падает;
- сбой модели на одной вакансии не роняет функцию: возвращаются замечания правил.

До готовности анализатора в репозитории лежит заглушка, возвращающая пустой список, — на ней собирается и проверяется вся остальная цепочка.

## Нормализованная вакансия

Тип `Vacancy` в `pv/models.py`. Главное:
- тексты очищены от HTML и лишних пробелов; пустая строка → `None`;
- `salary_min` и `salary_max`: `0` и отсутствие поля → `None`;
- `experience_years`: число из `requirement.experience`; `None`, если поля нет (ноль остаётся нулём — это «без опыта»);
- контактные данные (телефон, почта, контактное лицо) в `Vacancy` не попадают, в том числе в `raw`. В модель и в репозиторий они не уходят;
- `v.text_of("schedule")` — значение поля источника строкой. Цитата замечания должна быть подстрокой именно этого значения.

## Замечание

Тип `Finding` в `pv/models.py`. В отчёте выглядит так:

```json
{
  "topic": "schedule",
  "kind": "ambiguous",
  "field": "schedule",
  "quote": "Гибкий график",
  "problem": "Не указаны рабочие дни и время, конкретного расписания нет ни в одном поле.",
  "recommendation": "Уточните у работодателя рабочие дни, время начала и окончания работы и то, кто определяет расписание.",
  "source": "llm"
}
```

| Поле | Значения |
|---|---|
| `topic` | `title`, `duties`, `requirements`, `salary`, `schedule`, `location`, `employment` |
| `kind` | `missing` — пропуск, `ambiguous` — неоднозначность, `contradiction` — противоречие |
| `field` | поле источника из списка `SOURCE_FIELDS` (пути как в ответе API: `job-name`, `duty`, `requirement.qualification`, `addresses.address[].location` …) |
| `quote` | дословный фрагмент из этого поля; у пропуска — пустая строка |
| `problem` | в чём проблема |
| `recommendation` | что именно уточнить у работодателя |
| `conflict_with` | только у противоречия: `{"field": ..., "quote": ...}` — второе исходное значение |
| `source` | `rule` — нашло правило, `llm` — нашла модель |

Правила, которые проверяет `validate` (замечание, не прошедшее проверку, в отчёт не попадает):
- цитата есть в указанном поле дословно;
- у пропуска цитата пустая, у остальных — непустая;
- у противоречия есть второе значение, и оно тоже есть в своём поле.

Правила, которые кодом не проверить, но жюри проверит:
- в рекомендации нет вымышленных фактов («зарплата, вероятно, 50 000») и выводов о нарушении закона;
- если сведения есть в структурированном поле, их отсутствие в описании — не проблема;
- на понятной вакансии массив замечаний пустой. В учебном наборе таких четыре из десяти.

## Отчёт

```json
{
  "generated_at": "2026-11-25T09:00:00+02:00",
  "mode": "api",
  "source": "http://opendata.trudvsem.ru/api/v1/vacancies/region/39",
  "model": {"provider": "ollama", "model": "…", "used": true},
  "stats": {"vacancies": 200, "with_findings": 131, "findings": 342},
  "vacancies": [
    {"id": "…", "url": "https://trudvsem.ru/vacancy/card/…", "title": "…", "findings": [ … ]}
  ]
}
```

- `mode`: `api` или `file`;
- `url` — `null`, если ссылки в данных нет;
- `findings` — пустой массив, если замечаний нет;
- каждая входная вакансия присутствует в отчёте ровно один раз.

Файлы:
- `reports/latest.json` — текущий отчёт рабочего режима;
- `reports/history/` — прошлые отчёты;
- `reports/last_error.json` — последняя ошибка загрузки; при ошибке `latest.json` не трогается.

Папка `reports/` в репозиторий не попадает. Пример отчёта на учебных данных лежит в `examples/sample_report.json`.

## Команды

```
uv run python -m pv run                      # рабочий режим: API → отчёт (то же, что запускает расписание)
uv run python -m pv check examples/sample_vacancies.json --out reports/check.json   # проверочный режим
uv run python -m pv schedule                 # работать по расписанию из настроек
uv run pytest                                # тесты
```

## Настройки

Файл `config.toml` (образец — `config.example.toml`), каждую настройку можно переопределить переменной окружения. Ключи хранятся только в переменных окружения или в файле `.env`, который в репозиторий не попадает.

| Настройка | Переменная | По умолчанию |
|---|---|---|
| URL источника | `PV_SOURCE_URL` | `http://opendata.trudvsem.ru/api/v1/vacancies/region/39` |
| Расписание (cron) | `PV_SCHEDULE` | `0 6 * * *` |
| Максимум вакансий | `PV_MAX_VACANCIES` | `200` |
| Число потоков анализа | `PV_WORKERS` | `4` |
| Адрес модели | `PV_LLM_BASE_URL` | решает разработчик 2 |
| Имя модели | `PV_LLM_MODEL` | решает разработчик 2 |
| Ключ модели | `PV_LLM_API_KEY` | пусто |

## Правила работы

- Репозиторий публичный: никаких ключей, паролей, личных данных и настоящих резюме. Живые вакансии в репозиторий кладём без контактов.
- Каждый работает в своей ветке и своих файлах, вливает через запрос на слияние. Перед слиянием — `uv run pytest` зелёный.
- Сообщения коммитов — что сделано, по-русски.
- Вопрос, который задевает контракт, задаётся в общем чате сразу, а не решается молча.
