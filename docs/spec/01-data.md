# Часть 1. Данные и автоматизация

Исполнитель: владелец репозитория. Сначала прочитайте `00-contract.md`.

## Цель

Вся цепочка вокруг анализатора: получить вакансии из API или из файла, привести к единому виду, прогнать через анализатор, записать отчёт — по расписанию и вручную, без дублей и с сохранением последнего успешного отчёта при сбое.

Закрывает требования 1–8 и 13 из `docs/task.md`.

## Что должно работать

### Загрузка из API
- Постраничная загрузка (параметры `offset` и `limit`; как именно API считает `offset`, проверяется на живых данных), пока не набрано `max_vacancies` или не кончились данные. При лимите больше размера одной страницы загружается не меньше двух страниц.
- Таймаут на запрос и до трёх повторов с паузой: страница из 100 вакансий отдаётся около 15 секунд.
- Ответ со статусом не 200, не-JSON, без `results.vacancies` — ошибка загрузки с понятным текстом.
- Вакансия с тем же ID на двух страницах учитывается один раз.

### Загрузка из файла
- Тот же формат, что у ответа API: `results.vacancies[].vacancy`.
- Принимается также массив страниц и «голый» список вакансий — жюри может передать набор в любом из этих видов.
- Обращений к сети нет вообще.

### Нормализация
- По контракту `Vacancy`: чистка HTML и пробелов, `0` в зарплате → `None`, контакты отбрасываются.
- Вакансия без ID пропускается с предупреждением и считается в статистике.
- Незнакомые и отсутствующие поля не роняют разбор: живой API отдаёт больше полей, чем учебный файл, и не все из них есть у каждой вакансии.

### Анализ
- Вызов `analyze(v, llm)` в нескольких потоках (`PV_WORKERS`).
- Исключение в анализаторе на одной вакансии: вакансия остаётся в отчёте с пустым массивом и пометкой об ошибке, прогон продолжается.
- Замечания, не прошедшие `validate`, отбрасываются; их число пишется в статистику.
- Кэш: результат хранится по ID и отпечатку содержимого вакансии. Неизменившаяся вакансия заново в модель не отправляется — повторный запуск быстрый и даёт тот же результат.

### Отчёт
- Формат — в контракте. Каждая входная вакансия присутствует ровно один раз, порядок как во входных данных.
- Запись через временный файл и переименование: наполовину записанного отчёта не бывает.
- Рабочий режим: `reports/latest.json`, прошлый отчёт уходит в `reports/history/`.
- Сбой загрузки: `reports/latest.json` не меняется, пишется `reports/last_error.json`, сообщение на экран, код возврата не ноль.
- Проверочный режим пишет туда, куда указано в `--out`, и `latest.json` не трогает.

### Расписание
- `python -m pv schedule` — процесс, который сам запускает рабочий режим по cron-выражению из настроек.
- `.github/workflows/schedule.yml` — то же расписание в GitHub Actions плюс кнопка ручного запуска; отчёт сохраняется как артефакт.
- Ручной запуск — `python -m pv run`: тот же код, что по расписанию.

## Готово, когда

- `uv run python -m pv check examples/sample_vacancies.json --out reports/check.json` даёт отчёт с десятью вакансиями.
- `uv run python -m pv run` с лимитом 150 загружает две страницы и пишет `reports/latest.json`.
- Второй запуск подряд не обращается к модели и даёт те же замечания.
- С неверным URL: сообщение об ошибке, `latest.json` прежний, есть `last_error.json`.
- Тесты зелёные и не ходят в сеть.

## Порядок работы

1. Нормализация и загрузка из файла с заглушкой анализатора — после этого остальные части могут запускать проект.
2. Загрузка из API.
3. Отчёт, кэш, поведение при сбое.
4. Расписание.
