## Часть 3. Качество

### 1. Анализ проекта и проверка существующих материалов

Перед началом работы был изучен весь репозиторий и проверено соответствие текущих файлов спецификации docs/spec/03-quality.md и общему контракту docs/spec/00-contract.md. Зафиксирована работа строго в ветке db.
Установлено, что к началу работы в репозитории уже присутствовали и функционировали:

- скрипт оценки eval/score.py и модуль подсчёта метрик pv/scoring.py (на текущем отчёте examples/sample_report.json и reports/check.json показали полноту 1.00, точность 1.00, 0 лишних замечаний, в том числе 0 на чистых вакансиях);
- 12 собственных примеров со смысловыми ловушками eval/extra_vacancies.json и эталон к ним eval/extra_gold.json.
По итогам сверки был составлен план закрытия недостающих пунктов задания: создание тестов tests/test_score.py, выгрузка и очистка живого набора eval/real_sample.json, прогон анализатора на живых данных и оформление ручного аудита eval/review.md.

### 2. Создание тестов скрипта оценки (tests/test_score.py)

С нуля написан набор автоматических тестов tests/test_score.py, покрывающий логику подсчёта метрик в pv/scoring.py, консольный интерфейс eval/score.py и целостность эталонов.
В тестах проверены:
- идеальное совпадение отчёта с эталоном (полнота 1.0, точность 1.0, 0 лишних замечаний);
- корректная обработка допустимых замечаний (allowed не штрафуются ни при пропуске, ни при нахождении);
- снижение полноты при пропуске обязательных замечаний и срабатывание порогов прохождения;
- подсчёт лишних замечаний на проблемных и отдельно на чистых вакансиях (extra_on_clean), а также граничные значения порогов (recall = 0.9, extra_per_10 = 1.0);
- провал проверки при отсутствии вакансии из эталона в отчёте;
- дедупликация повторных пар (тема, вид) и работа на эталоне только из чистых вакансий;
- запуск CLI eval/score.py с проверкой кодов возврата (0 — пороги пройдены, 1 — ниже порогов, 2 — не переданы аргументы) и проверка на реальном отчёте examples/sample_report.json;
- соответствие ID, тем и видов замечаний в eval/gold.json и eval/extra_gold.json исходным наборам вакансий и контракту pv/models.py.
После создания выполнена проверка через uv run pytest tests/test_score.py — все тесты успешно пройдены.

### 3. Сборка и очистка живого набора данных (eval/real_sample.json)

Из открытого API портала «Работа в России» по Калининградской области (регион 39) выгружены 100 уникальных живых вакансий и сохранены в eval/real_sample.json в формате ответа API.
До сохранения файла в репозиторий выполнена очистка от всех контактных данных: удалены поля contact_list, contact_person, phone, phones, email, fax на верхнем уровне вакансий и внутри блока company, а также проведена проверка всех текстовых полей на наличие встроенных адресов электронной почты и номеров телефонов (утечек не обнаружено).
В tests/test_score.py добавлены две дополнительные автопроверки для eval/real_sample.json: проверка формата, количества уникальных вакансий (ровно 100), нормализации и полного отсутствия контактных данных, а также прогон всех 100 вакансий через правила анализатора без ошибок и отброшенных цитат. Всего в tests/test_score.py стало 14 тестов, все проходят успешно.

### 4. Прогон анализатора и составление отчёта ручного аудита (eval/review.md)

Выполнен проверочный прогон анализатора на eval/real_sample.json в режиме правил (--no-llm) с сохранением результата в reports/real_check.json. На 100 живых вакансиях анализатор отметил 14 вакансий (14 %), выдав 14 замечаний (11 по теме requirements и 3 по теме schedule), при нуле сбоев и нуле отброшенных проверкой цитат.
Для ручного просмотра воспроизводимым образом (seed = 39) отобраны 30 случайных вакансий из 100 и проверены по четырём критериям из спецификации. Результаты сведены в файл eval/review.md:
- выдуманные цитаты: 0;
- рекомендации с догадками или выводами о нарушении закона: 0;
- замечания не по делу (ложные срабатывания): 1 в выборке из 30 (требования были указаны внутри поля duty, а правило проверяло только requirements), дополнительно отмечены 3 схожих случая среди остальных 70 вакансий;
- пропущенные очевидные проблемы: 11 вакансий (12 проблем), сгруппированных в системные паттерны для доработки — сменный график без схемы и часов, противоречия по опыту с формулировками «6 мес.» / «полугода» / «одного года» / «без предъявления требований к стажу» и опытом внутри duty, текст с латинскими гомоглифами и отсылкой к собеседованию, несовпадение должности и обязанностей, конфликт уровня образования, размытый график в duty.
Все найденные проблемы зафиксированы в eval/review.md с точными ID вакансий для передачи разработчику Части 2, приложена полная таблица разбора всех 30 проверенных вакансий.

### 5. Итоговый статус

Все обязательные артефакты Части 3 (eval/gold.json, eval/score.py, eval/extra_vacancies.json, eval/extra_gold.json, eval/real_sample.json, eval/review.md, tests/test_score.py) подготовлены и проверены в ветке db. ### 3. Пункт 2 — Доработка импорта JSON и возврата к учебному набору в веб-панели (pv/web.py, pv/static/index.html)

Проанализирована работа кнопок «Проверить свой JSON…» (/api/check) и «Проверить учебный набор» (/api/check-sample). До исправления загрузка пользовательского JSON полностью затирала учебный набор, а нажатие соседней кнопки запускало повторный разбор всего учебного набора.
Выполнена аккуратная доработка без затрагивания остального функционала:
- в pv/web.py добавлено отдельное сохранение базового отчёта учебного набора в reports/check-sample.json (с автоматическим подхватом, если в reports/check.json уже сохранён учебный набор);
- при импорте пользовательского JSON (/api/check) анализируются только вакансии из загруженного файла (учебный набор не пересчитывается и не перекалибровывается), а результат объединяется с сохранённым учебным набором с сохранением метаданных imported_source и imported_ids;
- при импорте следующего JSON данные предыдущего импортированного файла автоматически удаляются и заменяются новыми поверх того же сохранённого учебного набора без его пересчёта;
- в pv/static/index.html при наличии загруженного JSON кнопка рядом меняет название на «Вернуться к учебному набору», импортированные вакансии помечаются в списке («· из JSON»), а нажатие кнопки (/api/check-sample?restore=1) мгновенно удаляет только данные импортированного JSON и возвращает сохранённый учебный набор без повторного анализа;
- обратная совместимость при отсутствии сохранённого учебного набора (пустая папка reports/) сохранена;
- в tests/test_web_extra.py добавлен тест test_upload_keeps_sample_replaces_prev_json_and_restores_without_reanalysis, покрывающий весь цикл (учебный набор -> первый JSON -> второй JSON -> возврат к учебному набору с нулевым числом повторных вызовов анализатора).
