1. Пункт 3 — Доработка списка неподтверждённых требований (not_confirmed) в сценарии резюме (pv/extra/resume.py)
--------------------------------------------------------------------------------
Суть задачи:
- В базовой реализации pv/extra/resume.py поле not_confirmed («чего вакансия требует, а резюме не подтверждает») проверяло только два структурированных поля: requirement.experience (число лет) и requirement.education (уровень образования).
- По спецификации docs/spec/04-extra.md результат черновика должен содержать список того, что требуется в вакансии, но не найдено в резюме, включая конкретные навыки, инструменты и документы из текстовых требований (requirements, а также опыт, указанный только в тексте).

Что нужно проверить на ревью / доработать:
- Проверить логику разбора текстовых требований и текстового опыта (в ветке уже есть локальная черновая правка в pv/extra/resume.py и тест test_not_confirmed_checks_text_requirements_and_text_experience в tests/test_web_extra.py — решить, принимать ли её, дорабатывать или откатить).
- Убедиться, что общие личные качества («ответственность», «активность»), необязательные формулировки («приветствуется», «опыт не обязателен», «обучение предоставляется») и условия работы не дают ложных срабатываний в not_confirmed.
- Убедиться, что инвариант resume.invented(draft, resume) == [] строго выполняется на всех примерах и живых вакансиях.
- При любых изменениях в pv/extra/resume.py пересобрать examples/sample_resume_draft.json.

2. Пункт 4 — Использование клиента модели pv/llm.py в сценарии резюме (pv/extra/resume.py)
--------------------------------------------------------------------------------
Суть задачи:
- В docs/spec/04-extra.md указано: «Модель берётся через тот же клиент pv/llm.py, что и в анализаторе».
- Сейчас pv/extra/resume.py работает полностью на эвристике/стемминге без обращения к pv/llm.py. Это быстро и гарантирует отсутствие выдуманных фактов, но текст сопроводительного письма и анализ пробелов жёстко шаблонные.

Что нужно решить и (при необходимости) доработать:
- Решить на ревью, оставлять ли сценарий полностью детерминированным (на правилах/стемминге) или добавить опциональный шаг с pv/llm.py (с фолбэком на правила при --no-llm / недоступной модели).
- Если подключать pv/llm.py: обязательно расширить проверку resume.invented() (проверять не только списки skills и work[].duties, но и сгенерированный текст summary / cover_letter, чтобы модель не могла приписать навыки или места работы, которых нет в исходном резюме).
- Покрыть работу с моделью тестом на подставном клиенте (без обращения к сети).

3. Мелкие отличия реализации от текста спецификации docs/spec/04-extra.md
--------------------------------------------------------------------------------
- Команда запуска CLI: в 04-extra.md приведён пример «uv run python -m pv.extra ...», в текущей реализации команда встроена в общий CLI как «uv run python -m pv resume ...» (модуля pv/extra/__main__.py нет). Проверить, соответствует ли это описанию в README.md.
- Имя файла тестов: в 04-extra.md указано «tests/test_extra.py», в проекте тесты лежат в «tests/test_web_extra.py».
- Автономная статическая страница web/index.html: в 04-extra.md предлагалась одна статическая HTML-страница без сервера, открывающая готовый файл отчёта (например, examples/sample_report.json) двойным щелчком. В проекте вместо этого сделана локальная веб-панель на FastAPI (uv run python -m pv web, файлы в pv/static/), где кнопка загрузки JSON принимает сырые вакансии и объединяет их с учебным набором. На ревью решить, нужен ли дополнительно оффлайн-файл web/index.html для просмотра готового отчёта без сервера.
- Передача своего файла резюме в CLI: команда «pv resume» сейчас всегда читает резюме из examples/sample_resumes.json (нет флага вроде --resumes-file для указания стороннего JSON с резюме).
- Проверка в README.md: убедиться, что в разделе «Свой сценарий» указана ссылка на сохранённый пример результата examples/sample_resume_draft.json.
